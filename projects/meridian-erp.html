Business systems / ERP / QA case study

Meridian ERP: from inventory transactions to an end-to-end manufacturing workflow.

An independently built, local manufacturing systems prototype exploring how purchasing, inventory, engineering BOMs, work orders, quality holds and traceability should behave as one coordinated process.

Python · FastAPI · SQLite · JavaScript · Local demo with fictional business data. Not a deployed enterprise ERP or a replacement for Infor.

The business problem

Inventory teams often have to reconcile disconnected purchase records, material receipts, item definitions and work-order status. A transaction can appear correct in one screen yet leave the next team with missing or inconsistent data. Meridian ERP explores the workflow controls needed to make those transitions explicit, testable and traceable.

My starting point

At Low Temp Industries, I work with Infor ERP job orders, item references, receiving/issuing transactions, cycle counts and discrepancy investigations. Meridian uses independent, fictional records to translate these operational concepts into a prototype; no employer source code or data is used.

What I built

A local API and dashboard demonstrating supplier purchase orders, stock receipts, versioned BOMs, work-order reservations and routing, production completion, nonconformance reviews, an audit ledger and optional simplified cost postings.

Workflow walkthrough

Follow one synthetic order across teams

01 / SupplySupplier PO & receipt
02 / InventoryStock ledger & reservation
03 / EngineeringActive BOM revision
04 / ProductionWork order & routing
05 / QualityBlocking checks & release
  1. Create or receive inventory using an approved supplier order; record the movement.
  2. Activate a bill of materials for the item to manufacture.
  3. Create a work order, reserve and issue required components, then complete routing operations.
  4. Prevent a finished-goods receipt while a high-severity quality nonconformance remains open.
  5. After required checks pass, post finished goods; inspect the ledger, audit trail and receipt history.

Technical decisions and verification

Workflow integrity

The project exercises revision-controlled BOM snapshots, reservations, an append-only movement ledger, nonconformance gates and idempotent receipt commands to reduce double-posting or inconsistent state.

API and persistence

FastAPI organizes application endpoints while SQLite supports the local demonstrator. The dashboard is JavaScript-based, with API documentation accessible locally.

Testable behavior

Pytest regression cases cover implemented workflows. GitHub Actions is configured to validate multiple Python versions and dashboard JavaScript. A workflow badge and test configuration are available in the repository.

Business constraints

Requirements and acceptance paths focus on material availability, preventing duplicate finished receipts, flagging severe quality issues and distinguishing illustrative accounting from production financial controls.

Defining acceptance criteria, testing negative paths, inspecting transaction results, documenting incomplete scope and breaking a complex business process into deliverable modules.

Scope, limitations and next steps

Meridian is a portfolio-grade local demonstration, not a commercial ERP deployment. It does not implement production authentication or tenant isolation, certified accounting, live Infor/SAP integrations, full inventory lot/serial controls, or a resilient hosted architecture. The accounting example is optional and deliberately simplified. No customer usage, employer ROI, production uptime or external certification is claimed.

The next engineering milestones would be production-grade access controls, tenant-aware data separation, richer inventory adjustments, documented external integration contracts and additional end-to-end regression evidence.
